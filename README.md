## Контрольные вопросы

### 1. Чем отличается Git от GitHub?
**Git** — это локальная программа (система контроля версий), которая работает на компьютере разработчика и отслеживает изменения в файлах проекта.
**GitHub** — это облачный сервис (хостинг), где хранятся удалённые копии Git-репозиториев и предоставляется веб-интерфейс для командной работы (Pull Request, Issues, Code Review).
Git может работать без GitHub, а GitHub без Git — нет.

### 2. Для чего используется виртуальное окружение Python?
Виртуальное окружение (`.venv`) изолирует зависимости конкретного проекта. Это нужно, чтобы:
- пакеты одного проекта не конфликтовали с пакетами другого;
- у каждого проекта была своя версия Python и свои библиотеки;
- файл `requirements.txt` описывал точный набор зависимостей, который можно воспроизвести на другом компьютере командой `pip install -r requirements.txt`.

### 3. Что такое commit, branch, remote, pull request?
- **commit (коммит)** — снимок состояния проекта в определённый момент времени с комментарием о том, что было изменено.
- **branch (ветка)** — независимая линия разработки, позволяющая работать над новой функциональностью, не затрагивая основную версию.
- **remote (удалённый репозиторий)** — копия репозитория на сервере (например, на GitHub). По умолчанию называется `origin`.
- **pull request (PR)** — запрос на слияние изменений из feature-ветки в `main` с обязательным код-ревью от коллег.

### 4. Зачем нужен файл .gitignore?
Файл `.gitignore` указывает Git, какие файлы и папки **не нужно** отслеживать и загружать в репозиторий. Обычно в него добавляют:
- виртуальное окружение `.venv/`;
- кэш Python `__pycache__/`;
- скомпилированные файлы `*.pyc`;
- файлы окружения `.env` (с секретами);
- настройки IDE `.idea/`, `.vscode/`;
- большие данные `*.csv`, `*.xlsx`.
Это уменьшает размер репозитория и предотвращает утечку конфиденциальных данных.

### 5. Как организовать командную работу над бизнес-приложением с помощью Git?
Стандартный процесс (Git Flow):
1. Каждый разработчик создаёт отдельную feature-ветку от `main` для своей задачи.
2. Работает в ней локально, делая регулярные коммиты с понятными сообщениями.
3. Отправляет ветку на GitHub командой `git push`.
4. Создаёт Pull Request с описанием изменений и назначает коллегу ревьюером.
5. После код-ревью и одобрения выполняется слияние (merge) в `main`.
6. Все разработчики обновляют свой локальный `main` через `git pull`.

### 6. Какие файлы обязательно должны быть в репозитории учебного проекта?
Минимальный набор:
- **README.md** — описание проекта, бизнес-задачи, стека, инструкции по запуску, автор;
- **.gitignore** — список исключений для Git;
- **main.py** (или `app.py`) — основной исполняемый файл;
- **requirements.txt** — список зависимостей с версиями для воспроизводимости окружения.
Дополнительно могут быть: `tests/`, `data/`, `docs/`.

### 7. Что произойдёт, если два разработчика изменят один и тот же файл в разных ветках?
При попытке слияния Git выдаст **конфликт слияния (merge conflict)**, потому что не сможет автоматически определить, какую версию строк оставить.
Решение:
1. Разработчик открывает файл в редакторе и видит маркеры конфликта (`<<<<<<<`, `=======`, `>>>>>>>`).
2. Вручную выбирает нужные изменения (или комбинирует их).
3. Удаляет маркеры, сохраняет файл.
4. Делает `git add` и завершает слияние коммитом.
Для предотвращения конфликтов команды договариваются о разделе ответственности за файлы и часто синхронизируют `main`.
